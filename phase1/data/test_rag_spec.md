> 本文档专门用于验证 PDFLoader 的双栏布局提取、表格物理顺序混排以及低文本扫描件判定等核心工业级功能。

## 1. 基础单栏文本测试
在 RAG（检索增强生成）系统的离线知识库摄入阶段，解析模块的健壮性直接决定了下游检索的精准度。如果解析出的文本格式混乱、顺序颠倒，即使使用最先进的向量模型，也无法召回正确的上下文。

## 2. 物理双栏布局测试 (Dual-Column Layout Test)
<!-- 使用 CSS 属性确保在转换为 PDF 时呈现标准双栏 -->

<div style="column-count: 2; column-gap: 30px; text-align: justify; font-size: 14px;">

### [左栏：向量检索与 Embedding 维度]
向量数据库在 RAG 架构中扮演着核心角色。我们将高维稠密向量存储在 PostgreSQL (pgvector) 或专门的向量数据库中。通过计算余弦相似度（Cosine Similarity），系统能够秒级找出与用户查询（Query）最相关的文本切块（Chunks）。为了确保检索的绝对精度，子块（Child Chunks）的 Token 大小通常限制在 150 到 200 之间。这种精细的分块策略可以极大减少检索噪声。

### [右栏：LLM 上下文窗口与生成限制]
当检索模块召回相关切块后，大语言模型（LLM）需要这些切块来生成最终答案。然而，LLM 具有硬性的上下文窗口限制，且过长的无用信息会导致大模型在生成时出现“迷失在中间”（Lost in the Middle）现象。因此，我们采用父子块双路索引。当检索命中精细的子块时，系统自动关联并加载其背后的父块（约 800 Tokens）送入模型，以平衡检索精度与生成上下文的完整度。

## 3. 表格物理顺序提取测试 (Table Interleaving Test)
在下面这个测试段落中，我们故意将一个复杂的系统性能对比表格夹在两段正文之间。**优秀的解析器应该能在输出中保持“正文 1 ➔ Markdown 表格 ➔ 正文 2”的物理阅读顺序**，而不是将表格无脑堆砌在页面最下方。

### [正文 1：系统评测准备]
我们对三个主流的 RAG 向量存储方案进行了基准测试（Benchmark）。测试环境为单台 16 核 32G 内存的服务器，使用 nomic-embed-text 向量模型，对 10 万条标准中文知识库文档进行并发写入和检索测试，以下是各系统的吞吐量与检索时延数据：

<!-- 测试表格 -->
| 存储引擎 (Engine) | 写入吞吐量 (QPS) | 平均检索时延 (Latency) | 混合检索支持 (Hybrid) | 内存占用 (Memory) |
| :--- | :---: | :---: | :---: | :---: |
| PostgreSQL + pgvector | 1,200 | 8.5 ms | 支持 (全文本 + 向量) | 较小 |
| Milvus (Standalone) | 3,500 | 4.2 ms | 仅限向量 | 中等 |
| Elasticsearch | 1,800 | 12.0 ms | 支持 (极其强大) | 较大 |

### [正文 2：评测结果分析]
通过上述表格数据可以看出，虽然 Milvus 在纯向量检索的写入吞吐量和时延上表现抢眼，但 PostgreSQL 凭借极其优秀的混合检索支持（Hybrid Search）以及极低的额外运维成本，成为了中小规模企业级 RAG 落地时的首选方案。
